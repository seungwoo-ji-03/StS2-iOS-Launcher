# In-app Steam Cloud sync

The phone keeps Slay the Spire 2 saves in step with Steam Cloud by itself, so a run started on a PC continues on
the phone and back. Code: `syncmgr/SyncManager.cs` (policy), `syncmgr/SteamCloudClient.cs` (network),
`syncmgr/IosNative.cs` (iOS runtime calls). Tests: `syncmgr/tests` (`make test`).

## Constraints

- **NativeAOT.** Godot 4.5's iOS export compiles all managed code ahead of time; there is no JIT and no
  `Reflection.Emit`. SteamKit2 cannot run (its protobuf-net serializer emits IL at run time), so the app uses a
  small hand-written Steam CM client: WebSocket connection, refresh-token logon, and the handful of
  `Cloud.*` service calls, with message classes generated by `protoc` for Google.Protobuf
  (definitions in `syncmgr/proto/`; regenerate with `syncmgr/proto/regen.sh`).
- **No Steam client on the phone.** The game's own cloud code (`SteamRemoteStorage`) is inactive on iOS, so the
  sync happens around the game rather than inside it.
- **The game holds saves in memory.** Writing a save file while the game runs is pointless (it is overwritten on
  the next save) or harmful. Local files are only written before the game reads them.

## When it runs

`cecilpatch --sync` inserts a call to `SyncManager.Boot()` at the start of `NGame.InitializePlatform`. That runs
on the main thread before `GameStartup` loads the profile, progress and preferences.

1. **Boot, live files** (blocking, 8 s budget): everything except run history. When it finishes, or when
   the budget runs out, local writes to live files are closed for the session.
2. **Boot, history** (background, after 3 s): run history files, which the game only reads when you open the
   history screen.
3. **Push** on `NOTIFICATION_APPLICATION_PAUSED` (app sent to background), inside a UIKit background task so iOS
   keeps the process alive until it finishes (25 s budget); and in `QuitSync()` before the in-game Quit ends
   the process. A push never writes local files.

Runs are serialized; a push cancels a history pull still in progress.

## Reconcile

Each file is compared three ways: the local copy (L), the cloud copy (C), and the base (B), the content both
sides last agreed on. B is the SHA-1 recorded in `user://sync_manifest.txt` after each sync. Steam's file list
already carries SHA-1 of every file, so unchanged files cost nothing.

| Situation | Action |
|---|---|
| L = C | nothing |
| L = B, C changed | take the cloud copy (boot only) |
| C = B, L changed | upload |
| both changed, or no base yet | compare progress; the losing copy is backed up |
| run file gone locally, C = B | the run ended here: delete it in the cloud |
| run file gone from the cloud, L = B | the run ended elsewhere: retire the local copy |
| run file gone locally, a fresh `*.corrupt` beside it | the game quarantined it: restore from the cloud |

Progress comparison (ported from Ekyso's `SaveProgressComparer`): floors climbed, then wins plus losses, then
discoveries, then playtime. Runs compare start time first (a newer run wins), then save time.

Guards:
- `progress.save` is never uploaded if the cloud copy has unlocks it lacks. An older game build drops content it
  does not know when it loads a save, and uploading would erase that content everywhere.
- Only valid JSON is written or uploaded. A save the game is writing at that moment is skipped. A zip left by an
  old build is treated as missing.
- Every overwritten or retired copy goes to `user://save-backups/<file>/` (last 20 each).

### Run history window

The game keeps only the newest run-history files in the cloud: 100 files and 5 MB per profile
(`OverwriteCloudWithLocalDirectory(historyPath, 5242880, 100)`). Older runs are *forgotten*: removed from the
cloud, kept on each device. The phone applies the same window. It uploads only runs inside it, forgets cloud
runs that fall out of it, and never re-uploads a run another device forgot.

## Cloud writes

All uploads and deletes of one sync go into a single app upload batch (`BeginAppUploadBatch`, each operation
with the batch id, `CompleteAppUploadBatchBlocking`), and the batch is always completed, even when the sync is
cancelled. Unbatched operations that are interrupted stay pending on Steam's side. Enough of them make Steam
refuse every write with `TooManyPending` (108) for a while. On the first 108 the sync stops and tries again next
time rather than retrying file by file.

Large files are stored zipped (one entry). Downloads are unzipped before comparison or writing.

## Login

`make login` (desktop, QR code) creates a Steam refresh token; `make provision` copies it into the app as
`user://steam_token.json`. The app renews it when Steam offers a new one: the old token becomes invalid, so the
new one is written atomically and the previous file kept as `.prev`. If Steam rejects the login (expired,
revoked, changed password), sync stops, and `sync_status.txt` / `sync_log.txt` say so (`make logs`).

## Not covered

- Two devices playing at the same time: the later push wins where progress comparison allows, and the other
  copy stays in backups. There is no field-level merge.
- `settings.save` is device-local on purpose (frame rate, MSAA and window options differ per device).
